# Результат проверки хранилища `storage.quantumart.ru`

Дата проверки: **2026-10-05**. Перенесено **98 файлов, 1.47 ГБ** с
`storage.qp.qsupport.ru`. Байты лежат ассетами GitHub Release
[`QuantumArt/storage`](https://github.com/QuantumArt/storage) тега `v1`,
раздаёт их nginx на VPS редиректом 302.

**Итог: 98 из 98 файлов подтверждены двумя независимыми способами, релиз `v1`
закрыт — 98 ассетов, 1.47 ГБ.** В процессе найдено 3 битых файла (перекачаны)
и 2 имени, которые нельзя сохранить как есть (переименованы). Оба случая
разобраны ниже — это не мелочи, а ошибки, которые выглядели бы как «всё на
месте».

---

## 1. Почему одной проверки недостаточно

У оригинала **нет эталонных хешей**: `Content-Length` и ETag вида
`1d823d98269e4a4` (метка IIS «время+размер»), а не хеш содержимого. Значит,
сверить файл «с оригиналом» нечем, и остаются два рубежа:

| Рубеж | Что проверяет | Чей результат |
|---|---|---|
| **Целостность формата** — `unzip -t`, `tar -tzf`, маркеры `%PDF`/`%%EOF` | что архив цел | производитель (Quantum Art) |
| **Сверка двух загрузок** — локально и независимо на VPS | что байты те же | вторая машина, другой код |

**Ловушка, на которую легко наступить:** манифест `manifest/manifest.json`
вычислен из того же скачивания, что и файлы. Битый файл даёт битый же хеш, и
сверка «файл против манифеста» всегда зелёная. Она не доказывает ничего.
Поэтому в репозитории лежит `manifest/reference-sha256.txt` — хеши из
независимого скачивания на VPS, и сверка идёт против них, а не против
собственного манифеста.

## 2. Что было сломано и что сделано

### 2.1 Три битых файла — молча, с правильным размером

`curl -C -` (докачка) на этом хостинге даёт битые файлы: после обрыва соединения
сервер один раз отвечает `200` вместо `206`, и curl дописывает файл целиком к
остатку. Один файл при этом оказался **259.9 МБ вместо 175.1 МБ**.

| Файл | Симптом | Что сделано |
|---|---|---|
| `QP8.zip` | `invalid compressed data to inflate QP8.exe` | перекачан кусками |
| `QP8.ProductCatalog.zip` | `invalid compressed data to inflate` | перекачан кусками |
| `QP8.Widgets.Pg.zip` | `bad zipfile offset` | перекачан кусками |

**Второй независимый проход (VPS) показал те же три файла** — два метода
указали на один и тот же набор, значит битые были именно они.

Итог: 95 из 98 локальных копий совпали с VPS побайтово сразу, три перекачаны и
после этого дали 98/98.

### 2.2 Два имени, которые нельзя сохранить

| Было | Стало | Почему |
|---|---|---|
| `qp8-pg-functional-сharacteristics.pdf` | `qp8-pg-functional-characteristics.pdf` | в имени кириллическая «с» (U+0441); такое имя приходится перцент-энкодить в каждой ссылке |
| `QP_Setup_7.9.7.0..zip` | `QP_Setup_7.9.7.0.zip` | **GitHub схлопывает двойную точку** при загрузке ассета: имя с `..` превращается в `.zip`. Проверено и созданием релиза, и перезаливом |

Содержимое обоих файлов не менялось, sha256 совпадает с оригиналом, исходные
имена сохранены в манифесте полем `original_name`.

**Второй случай опаснее.** Наш nginx имя пропускает, редирект 302 формируется
без ошибок, ссылка выглядит безупречно — и ведёт на ассет, которого в релизе
нет. Пользователь получил бы 404 по ссылке, прошедшей любую поверхностную
проверку. Пойман сверкой имён ассетов с манифестом.

### 2.3 Дыра в самом сервисе

`/downloads/<любое несуществующее имя>` отдавал **302 на несуществующий ассет**:
посетитель получал страницу 404 от GitHub вместо ответа своего хранилища.
Исправлено: nginx сверяется со списком из манифеста (`assets.conf`,
генерируется `tools/build_index.py`) и отдаёт 404 сам.

## 3. Обязательные негативные тесты

Проверка, которую нельзя заставить ошибиться, не доказывает ничего. Каждая
проверка прогнана на заведомо негодных данных:

| Проверка | Негативный тест | Результат |
|---|---|---|
| Сверка с эталоном | файл испорчен в середине, **размер сохранён** | пойман, перекачан |
| `fetch_on_vps.sh` | zip испорчен на 4 КБ в середине, размер прежний | пойман (до правки — проходил как годный) |
| `fetch_on_vps.sh` | файл обрезан вдвое | пойман, перекачан |
| Сверка ассетов релиза | подставлен заведомо неверный эталон | отказ, как и ожидалось |
| Список ассетов в nginx | запрос несуществующего имени | 404 от своего хранилища |

## 4. Сквозная проверка раздачи

Проверено на живом контейнере, вся цепочка:

```
http://127.0.0.1:3023/downloads/QP8_ProductCatalog_Postgres_Pro.pdf
  → 302  https://github.com/QuantumArt/storage/releases/download/v1/…
  → 302  https://release-assets.githubusercontent.com/…
  → 200  222 262 байта, sha256 0c768ea41432b6e611ecffeb7a20b189
```

sha256 совпал с эталоном.

Оба **переименованных** файла проверены так же — это важно, потому что именно
на них最容易 ошибиться:

| Файл | Результат |
|---|---|
| `QP_Setup_7.9.7.0.zip` (было `..zip`) | 200, 35.0 МБ, 2 редиректа, **sha256 совпал** |
| `qp8-pg-functional-characteristics.pdf` (было с кириллической «с») | 200, 0.3 МБ, 2 редиректа, **sha256 совпал** |

Проверять кодом ответа на `/` бессмысленно: страница
индекса отдаётся даже тогда, когда ни один файл не отдаётся. На соседнем
проекте `nuget` именно так не заметили сбой — `/v3/index.json` отдавал 200,
healthcheck был зелёным, а файлы не открывались. Поэтому `deploy.sh` (шаг 5)
скачивает файл по всей цепочке и сверяет хеш, и это блокирующая проверка.

## 4a. Приёмка на VPS (2026-10-05)

Домен поднят на `217.198.6.66`, TLS от Let's Encrypt (CN=storage.quantumart.ru,
действует до 2027-01-03). Проверено **с внешней машины**, а не с сервера: с
сервера любой сбой DNS или маршрутизации не виден.

| Проверка | Результат |
|---|---|
| `GET /` | 200 |
| `GET /healthz` | 200 |
| `GET /downloads/QP8.zip` | 302 → `github.com/QuantumArt/storage/releases/download/v1/QP8.zip` |
| `GET /downloads/` | 404 |
| `GET /downloads/nope.zip` | 404 |
| Сквозное скачивание `qp8-admin-man.pdf` (1.5 МБ) | 200, **sha256 совпал** |
| Сквозное скачивание `QP_Setup_7.9.7.0.zip` (35.0 МБ) | 200, **sha256 совпал** |
| Сквозное скачивание `qp8-pg-functional-characteristics.pdf` (0.3 МБ) | 200, **sha256 совпал** |
| `tools/verify.py --live` по всем 98 файлам | **код 0, расхождений нет** |

Три скачивания подобраны не случайно: два из них — те самые, которые пришлось
переименовать. Раньше всего здесь ломалось именно на них.

**Что пришлось починить на сервере, чего не видно из репозитория:**

1. **`unknown directive "http2"`** — в конфиге стоял `http2 on;` (nginx ≥ 1.25),
   на сервере версия старее. Заменено на `listen 443 ssl http2`, как у соседних
   доменов. Синтаксис проверен локально в `nginx:1.27-alpine` **до** повторной
   правки на сервере.
2. **`~/storage` уже существовал** (ради `.secrets/cloudflare.ini`), поэтому
   `git clone` падал. Код взят инициализацией на месте — клон поверх затёр бы
   секреты.
3. **`git pull` без токена** дал бы 403 из-за общего
   `/root/.git-credentials` и уронил бы деплой на `set -e`. Теперь шаг
   пропускается с предупреждением.

### 4b. Приёмка 15 документов quantumart (2026-10-05)

Документы, на которые ссылается `quantumart.ru`: 14 PDF + 1 DOCX, 18.9 МБ.
Перенесены в релиз `v1`, отдаются с `https://storage.quantumart.ru/downloads/<файл>`.

| Файл | Результат сквозного скачивания |
|---|---|
| `privacy_policy_Quantumart_2022.pdf` | 200, 0.3 МБ, sha256 совпал |
| `certificate_bitrix.pdf` | 200, 0.2 МБ, sha256 совпал |
| `case_vtb.docx` | 200, sha256 совпал |
| `Summary_statement_2018-2025.pdf` | 200, 5.0 МБ, sha256 совпал |

**Ошибка, которую я差点 не заметил.** Первый прогон `verify.py --live` отрапортовал
об успехе, проверив **98** файлов вместо 113: инструмент читал
`manifest/mapping.json`, а это маппинг переноса ссылок портала downloads, и 15
документов quantumart из него просто не выводились. Зелёный отчёт при четверти
непроверенного состава — ровно тот класс ошибки, что и манифест из собственного
скачивания. Исправлено: `verify.py` читает полный `manifest/manifest.json`, а
`--scope` сужает проверку осознанно. После правки — 113/113.

**Ещё одна, того же класса.** `docker compose` падал на 113 именах с
`could not build map_hash, you should increase map_hash_bucket_size: 64` — на 98
работало, на 113 контейнер уходил в рестарт с exit 1. Размер хеш-таблицы карты
теперь считается из числа файлов при генерации.

**Третья — в `deploy.sh`.** Шаг `git pull` пропускался при отсутствии токена, а
репозиторий публичный и токена не требует: из-за этого деплой собирал устаревший
образ, а новые файлы не доезжали до сервера. Теперь публичный репозиторий
тя��ется анонимно, и ручной `git merge` перед деплоем не нужен.

## 6. Что осталось непроверенным

Честная граница: **побайтовое тождество с тем, что лежит на оригинале, не
доказано.** Оригинал не публикует хешей, а единственный способ получить
гарантию — повторно скачать 1.47 ГБ и сверить, что и было сделано (98/98 через
VPS). Если оригинал отдаёт разные байты для одного и того же пути в разные
моменты, этот класс расхождений не ловится никаким сравнением хешей — тогда
помогла бы сверка внутренних CRC архивов между двумя загрузками. Не проверено.

## 7. Как перепроверить

```bash
# 1. Файлы против независимого эталона + целостность формата
python3 tools/verify.py --local

# 2. Ассеты релиза анонимно, без токена (проверка с токеном прошла бы
#    и у приватного репозитория, а раздавать ассеты приватного нельзя)
python3 tools/verify.py --release

# 3. Живые ссылки, когда домен поднят
python3 tools/verify.py --live
```

Код возврата `0` — расхождений нет, `1` — есть, подходит для CI.
